# 노드 기획 PRO — 계획 및 구조 설계

> 대상: 자유롭게 기획하고 직접 만들어 보고 싶은 사람 (초등 저학년용 "노드 기획 놀이터"와 별개 앱)
> 핵심 가치: **기획(노드) → 점검 → AI에게 정확히 지시(프롬프트)** 를 한 흐름으로

## 1. 범위 (1단계)

| 순서 | 기능 | 한 줄 설명 |
|---|---|---|
| M1 | 기반 + 그래프 편집기 | 노드/선 편집, 프로젝트 저장, JSON 가져오기·내보내기 |
| M2 | **프롬프트 컴파일러** | 그래프 → 정규화된 명세(IR) → AI 도구별 지시문 |
| M3 | **기획 점검(린트)** | 규칙 기반 점검 + 클릭하면 해당 노드로 이동, 컴파일러에 점검 결과 반영 |
| M4 | 다듬기 | 선택적 AI 점검(프록시), 예시 프로젝트, 사용 안내 |

범위 밖(2단계 이후): 상태·조건 변수 실행, 디바이스 프레임, 모둠 공동 편집, 사용자 테스트 모드, 버전 비교.

## 2. 기술 스택

- Vite + React + TypeScript + Tailwind
- 노드 캔버스: React Flow (`@xyflow/react`)
- 상태: zustand (그래프 + UI 상태 분리)
- 검증: zod (프로젝트 스키마, 가져오기 파일 검증)
- 저장: 1단계는 localStorage + JSON 파일 (Supabase는 협업 단계에서 도입)
- AI(선택, M4): Vercel 서버리스 `api/` 프록시 → Gemini/Claude. **API 키는 프론트 노출 금지**
- 배포: Vercel
- 테스트: Vitest (린트 규칙·컴파일러는 순수 함수라 단위 테스트가 쉬움)

## 3. 폴더 구조

```
node-planner-pro/
├─ docs/01-plan/            # 이 문서
├─ api/                     # (M4) AI 프록시 서버리스 함수
├─ src/
│  ├─ core/                 # UI와 무관한 순수 로직 (가장 중요)
│  │  ├─ schema.ts          # Project/Node/Edge 타입 + zod
│  │  ├─ graph.ts           # 순회·도달성·진입/진출 계산
│  │  ├─ ir.ts              # 그래프 → 정규화 명세(IR)
│  │  ├─ lint/              # 점검 규칙 (rules/*.ts + engine.ts)
│  │  └─ compile/           # targets/*.ts (claude, gemini, builder, markdown)
│  ├─ store/                # zustand (project, ui)
│  ├─ features/
│  │  ├─ canvas/            # React Flow 캔버스, 노드 컴포넌트
│  │  ├─ inspector/         # 선택한 노드 속성 편집
│  │  ├─ lint-panel/        # 점검 결과 목록
│  │  └─ compile-panel/     # 대상 선택, 미리보기, 복사
│  ├─ lib/                  # storage, export/import
│  └─ examples/             # 예시 프로젝트 JSON
└─ tests/                   # core 단위 테스트
```

원칙: `core/`는 React를 import 하지 않는다. UI를 바꿔도 점검·컴파일 결과가 그대로여야 한다.

## 4. 데이터 모델 (schema.ts)

```
Project { version, name, goal, audience, nodes[], edges[], tokens?, meta }

Node (type별 data)
  screen    : 이름, 목적, 보이는 것, 진입 조건(공개/로그인 필요)
  component : 종류(버튼/입력/목록/이미지/폼…), 이름, 소속 screen
  data      : 저장소 이름, 필드[{이름,타입}], 저장 위치(local/DB)
  logic     : 조건 설명, 참/거짓 분기
  external  : 외부 서비스/API 이름, 용도
  note      : 자유 메모 (명세에는 "참고"로만 포함)

Edge { from, to, kind: navigate | save | read | trigger | branch, label? }
```

- 시작 화면은 `screen` 노드의 `isStart` 플래그로 표시한다.
- 파일의 `version` 필드로 이후 스키마가 바뀌어도 마이그레이션할 수 있게 한다.

## 5. 프롬프트 컴파일러 설계 (M2)

파이프라인: **Project → IR → Target 템플릿 → 텍스트**

IR(중간 표현)에 정리하는 것:
- 앱 개요(목표, 대상)
- 화면 목록과 화면별 구성요소
- 화면 이동 흐름(출발 → 도착, 조건)
- 데이터 모델과 읽기/쓰기 관계
- 외부 연동
- 인수 기준(화면 이동·저장 동작마다 "~하면 ~된다")

출력 대상(프리셋):
| 대상 | 특징 |
|---|---|
| Claude Code / Cursor | 파일 구조 제안, 단계별 구현 순서, 확인 방법 포함 |
| 범용 AI 빌더(Lovable·Bolt·v0) | 화면 중심, 한 번에 붙여넣는 한 덩어리 |
| Gemini / ChatGPT | 대화형, 먼저 질문하고 시작하도록 유도 |
| Markdown 기획서 | 사람이 읽는 문서 (PDF/공유용) |

공통 포함: 기술 제약(스택 선택), **보안 지침**(키 프론트 노출 금지, DB 권한 규칙), "하지 말 것" 목록.
점검 결과가 있으면 "아직 정해지지 않은 부분"을 지시문 끝에 명시해 AI가 임의로 추측하지 않게 한다.

## 6. 기획 점검(린트) 설계 (M3)

규칙은 `(project) => Issue[]` 순수 함수. Issue = `{ id, severity, nodeIds, message, hint }`.

| ID | 심각도 | 점검 내용 |
|---|---|---|
| L001 | 오류 | 시작 화면이 없음/둘 이상 |
| L002 | 오류 | 시작 화면에서 도달할 수 없는 화면 |
| L003 | 경고 | 막다른 화면 (나가는 이동이 없음) |
| L004 | 경고 | 구성요소가 하나도 없는 빈 화면 |
| L005 | 경고 | 화면에 연결되지 않은 구성요소/데이터 노드 |
| L006 | 경고 | 읽기만 하고 저장하는 곳이 없는 데이터 |
| L007 | 경고 | 입력/폼이 있는데 저장 연결이 없음 |
| L008 | 제안 | 목록/데이터 화면에 "비어 있을 때" 안내 없음 |
| L009 | 제안 | 로그인 필요 화면이 있는데 로그인 화면이 없음 |
| L010 | 제안 | 이름이 같은 화면/노드 중복 |
| L011 | 제안 | 목적(설명)이 비어 있는 화면 (AI가 추측하게 됨) |

UI: 점검 패널 목록 → 클릭 시 캔버스가 해당 노드로 이동·강조. 오류가 있으면 컴파일 시 경고 배너 표시(막지는 않음).

## 7. 마일스톤별 완료 기준

- M1: 노드 추가/연결/편집, 새로고침 후 복원, JSON 내보내기·가져오기(잘못된 파일 거부)
- M2: 예시 프로젝트 3개 이상에서 4개 대상 지시문 생성, 단위 테스트 통과
- M3: 규칙 L001~L011 단위 테스트 통과, 의도적으로 결함 있는 예시에서 기대한 이슈 검출
- M4: AI 프록시 경유 호출 확인(키가 번들에 없음), 예시/안내 완비

## 8. 위험과 대응

- 노드가 많아질 때 성능 → React Flow 기본 가상화 + 선택 구독으로 대응
- 지시문이 길어짐 → 대상별 길이 가이드와 섹션 토글 제공
- 점검 규칙 과다 경고로 피로감 → 심각도 3단계 + 규칙별 끄기
